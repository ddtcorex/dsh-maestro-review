# AGENTS.md: dsh-maestro-review

> `CLAUDE.md` is a symlink to `AGENTS.md`. Only edit `AGENTS.md`.

## Purpose

The DeepSeek Harness (DSH) host plugin of Maestro Review. The review engine
and the CI flow live in `@ddtcorex/maestro-reviewer`; this package adds what
only a developer's DSH host does with it.

Names by boundary: npm package = `@ddtcorex/dsh-maestro-review`; Cordis rows =
`maestro-review-plugin` (the package root; DSH serves the client bundle only
for a row naming the bare package), `maestro-review-webhook`,
`maestro-review-host-orchestrator`, `maestro-review-settings-rpc`, plus the
`connection` entry; RPC channel `/dsh-maestro-review`; Settings section
`maestro-review`, order 32. Settings keys and the `dsh-maestro-review/` data
directory are unchanged from the package's earlier life as the whole reviewer.

## Layout

- `src/host/providers/gitlab.ts`: webhook routes; `review-intake.ts`: payload routing; `secure-compare.ts`: constant-time secret comparison.
- `src/host/host-orchestrator.ts`: settings, mappings, trigger gates, worktree, vendor and govard helpers, the unmapped-deep decline, the Telegram digest, then `ctx.reviewEngine.run`.
- `src/host/settings-rpc.ts`, `config-store.ts` (flat adapter over the store), `vendor/store.ts` (hash-sealed copy generated by `dsh-maestro-core`'s `scripts/vendor-store.mjs`, never hand-edited), `notify.ts`, `events.ts` (the `maestro/review-request` event, `reviewRunner` and the redeclared `reviewEngine` service).
- `src/client/`: the Settings section; `scripts/build-client.mjs` bundles it into `lib/client.js`.

## Engine dependency

The engine is `workspace:^` on the sibling checkout `../../maestro-reviewer`
(published as a caret range of the engine version). Import engine modules only
through `@ddtcorex/maestro-reviewer/lib/...` paths listed in the engine's
`tests/engine-exports.test.ts`, and take its types from the engine (for
example `EngineRunOptions['model']`, `toModelSelection`): a second copy of a
DSH package here brands types differently and only typechecks while an install
has relinked the engine's `node_modules`. Every `pnpm install` here relinks
the engine's `node_modules` into this package's store; reinstall the engine
afterwards (`scripts/build-all.sh --install` orders it) before trusting
`check-standalone-installs.sh`.

## Merge order and the lockfile

`pnpm-lock.yaml` records the engine checkout as the importer
`../../maestro-reviewer`, and CI clones the engine's `master` there. So:

- A plugin PR that needs an engine change goes green only after that engine
  change is merged; merge the engine first, then re-run the plugin CI.
- Any dependency change on the engine's `master` makes this package's frozen
  install fail with `ERR_PNPM_OUTDATED_LOCKFILE`: regenerate the lockfile here
  (`pnpm install` with the engine checkout on that `master`) and commit it.

## Release checklist

1. The engine release (`@ddtcorex/maestro-reviewer`) is published first: this
   package's release workflow builds against the engine's `master`, and
   `pnpm publish` rewrites `workspace:^` to a caret range of that version.
2. Bump `package.json` and `CHANGELOG.md` on `chore/release-X.Y.Z`; verify,
   build and test; PR, CI green, human `APPROVED`, merge.
3. Tag `vX.Y.Z` and push the tag only after an explicit approval; the
   `release.yml` workflow publishes. Never publish by hand.
4. Validate on a dry-booted host before switching a live profile: no
   `did not activate`, `/dsh-maestro-review` answering 401, the Settings
   section rendered, and one webhook review on a disposable MR.
